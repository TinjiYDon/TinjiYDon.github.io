我把 RAG 从神坛上拿下来：一节 65 分钟的课教我的事

短片段上，RAG 把召回从 0.42 拉到 0.82；长课上，它只有 25.5%，输给把整节课塞进上下文的模型。这不是 bug，是边界。

RAGAgent项目复盘
约 2 分钟

先看结论

  • 短片段：召回 0.416 → 0.824，答案命中 22.9% → 58.0%。
  • 长课（64.95 分钟）：检索 25.5%，全上下文 41.8%。
  • 成本约为全上下文的 1/25，但长课的效果是拿钱换的。

项目做到第三个月，我们拿到一个很难看的结果。

短片段上，RAG 把召回从 0.42 拉到 0.82。长课上，它只有 25.5%，而把整节课塞进上下文的模型是 41.8%。

我不服。

先查检索，再换 chunk 大小，最后换 embedding。都没用。后来才承认：这不是 bug，是边界。

短片段：它真的有用

我们做的是课堂复习。一节课 45–90 分钟，学生想找的往往是一句话、一个公式、一页 PPT。

短片段里，答案通常就在一页 PPT、一段字幕里。检索把那一页找出来，模型就能答。

那组测试里，答案命中率从 22.9% 涨到 58.0%。这是 RAG 最舒服的场景：局部、要引用、要拒答。

长课：它为什么突然不灵

长课的问题不一样。

学生问“这节课和上节课的模型有什么区别”，答案可能散在三四个章节里。检索每次只给回几个片段，模型看不到全局。

这不是检索的 bug，是它的工作方式。它只负责“找局部”，不负责“串起来”。

所以我们没赢。全上下文 41.8%，我们 25.5%。

但成本这边，混合检索大约是它的 1/25。省下来的钱，有一部分是拿效果换的。

我改了三件事

先定编排，再写 Prompt。

最早想把流程塞进一个 Prompt，结果一长就散：答错了，不知道是检索错、工具错，还是生成错。后来拆成意图路由 + 3–4 条子工作流，每一步单独看日志，才定位得到问题。

先建评测集，再做功能。

没有固定题集时，每次改动都在新题上试，说不清是变好还是换题了。补了 CEQA 之后，才敢说“这次有效”。前期慢，但比反复返工便宜。

先把入口收住，再接工具。

工具能“做事”，但没有统一入口时，鉴权、限流、审计要在每处重写，出问题也难复现。后来补了 API Gateway，请求都从那里进，才把线收住。

所以，什么时候该用 RAG

  • 用户要定位、引用、拒答：用检索。
  • 用户要整节课 / 整份文档的全局理解：先全上下文，或者先做分块摘要。
  • 预算紧、问题局部：检索最划算。
  • 预算够、问题全局：别硬上 RAG。

这次项目教会我的，不是“RAG 不行”，而是“RAG 有边界”。承认边界，比多接一个模型有用。
